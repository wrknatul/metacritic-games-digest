# Metacritic Games Digest

Сервис раз в час обходит раздел Games на Metacritic и берёт 20 игр, которые сегодня ещё не обрабатывал. Он сохраняет карточку игры с оценками по каждой платформе. LLM пишет короткое резюме: что нравится и что не нравится, отдельно критикам и отдельно игрокам. Для каждой игры сервис находит самый популярный летсплей на YouTube, переводит речь блогера в текст и делает по нему заключение. В веб-интерфейсе есть список игр, карточка, похожие игры и живой мониторинг воркеров.

- Сервис: https://games-digest-lutan.netlify.app
- Мониторинг: https://games-digest-lutan.netlify.app/monitor
- Переписка с нейросетью: JSONL приложены к письму

## Что сделано по пунктам ТЗ

| Пункт ТЗ | Как сделано |
| --- | --- |
| Раз в час 20 новых игр, которые сегодня не обрабатывались | APScheduler внутри процесса, интервал 60 минут. Таблица `daily_processed` хранит, что уже взято сегодня. День считается по Москве |
| Первые 20 игр из New Releases на `/game/` | Первый запуск дня парсит секцию New Releases на https://www.metacritic.com/game/ |
| Дальше SEE ALL, сортировка «Новые», по странице за заход | Курсор `daily_cursor` помнит страницу https://www.metacritic.com/browse/game/all/all/all-time/new/?page=N. Если на странице осталось 4 необработанные игры, следующий запуск возьмёт их и 16 со следующей страницы |
| Каждый новый день заново | На новую дату заводится новый курсор: снова New Releases, потом SEE ALL с первой страницы. Игры, которые уже есть в базе, обновляются |
| Название, обложка, платформы с Metascore и Userscore, разработчик, описание, видео | Таблицы `games` и `game_platforms`. Userscore запрашивается отдельно по каждой платформе |
| Резюме отзывов отдельно для критиков и для игроков, обновляется при повторных обходах | Выборка отзывов по тональности, LLM со structured output. Резюме пересобирается только когда меняется выборка (сверяется отпечаток) |
| Веб: список, карточка, фильтр по платформам, поиск, сортировка по рейтингу | `/`: поиск по названию, фильтр по платформе, сортировка по Metascore, Userscore, дате выхода или названию. `/games/{slug}`: полная карточка |
| Похожие игры из базы, клик открывает карточку | TF-IDF по описаниям, совпадение жанров, серии и разработчика. Под каждой похожей игрой написано, чем она похожа |
| Доп. 1: самый популярный летсплей, речь в текст, заключение | Поиск через yt-dlp, выбор ролика с наибольшим числом просмотров, три способа получить текст, заключение от LLM |
| Доп. 2: мониторинг в реальном времени и кнопка запуска | `/monitor` по SSE: воркеры, этапы, прогресс запуска, счётчики, расход LLM, журнал. Кнопка «Запустить обработку сейчас» |

## Архитектура

```
APScheduler (раз в час) ─┐
кнопка /api/runs ────────┴─> Pipeline.start()
                               │
                               ├─ select_games(): New Releases → SEE ALL стр. N (курсор дня)
                               │
                               ├─ detail-воркеры ×4 (asyncio) ─ Metacritic JSON: карточка, оценки, отзывы
                               │                             └─ LLM: резюме критиков / игроков
                               │        │ игра сохранена
                               │        ▼
                               └─ letsplay-воркер ─ YouTube поиск → речь в текст → LLM-заключение
                                                       │
SQLite (WAL, том Fly) <────────────────────────────────┘
FastAPI: HTML-страницы, JSON API, SSE /api/monitor/stream <── Monitor (состояние воркеров в памяти)
```

| Файл | Что внутри |
| --- | --- |
| `app/metacritic.py` | Парсинг списков из HTML, карточки и отзывы из backend JSON, ретраи |
| `app/pipeline.py` | Запуск: выбор игр на сегодня, очереди и воркеры, upsert, летсплеи |
| `app/llm.py` | OpenRouter: резюме, речь в текст, заключение. Structured output, Pydantic, повтор при битом JSON |
| `app/letsplay.py` | Поиск и выбор летсплея, субтитры, вырезка аудио |
| `app/similar.py` | Похожие игры |
| `app/monitor.py` | Состояние воркеров, текущего запуска и журнал для `/monitor` |
| `app/main.py` | FastAPI: страницы, API, SSE, планировщик |

## Решения и почему

**Источник данных.** Списки игр берутся из HTML-страниц, названных в ТЗ: секция New Releases и сетка SEE ALL. Карточки и отзывы берутся из `backend.metacritic.com`. Это JSON API, который вызывает сам фронтенд metacritic.com, с публичным ключом из его страниц. Там есть оценки по каждой платформе и отзывы с фильтром по тональности, а вёрстку Metacritic регулярно меняет. Если секция New Releases перестала парситься, запуск не падает: он пишет предупреждение в журнал и берёт игры из SEE ALL.

**Выборка отзывов для резюме.** Если взять первые 50 отзывов, получится одна похвала: API сортирует их по оценке. Поэтому выборка строится по тональности. Критики: до 12 положительных, 8 смешанных и 8 отрицательных. Игроки: 20, 12 и 20. Отзывы короче 25 символов отбрасываются. LLM получает выборку и общее распределение оценок, чтобы не раздувать редкий негатив.

**Резюме обновляются при повторном обходе, но не каждый раз.** От выборки отзывов считается SHA-1. Если отпечаток тот же, LLM не вызывается и остаётся прежнее резюме. Если появились новые отзывы, резюме пересобирается. Каждый новый день New Releases обходятся заново, и без этой проверки сервис платил бы за одно и то же.

**Защита от расходов.** В БД ведётся дневной лимит вызовов LLM (`LLM_DAILY_CALL_LIMIT`, по умолчанию 400) и учёт токенов и стоимости в долларах по данным OpenRouter. Всё это видно на `/monitor`. У игр без отзывов, а это большая часть хвоста SEE ALL, запросы отзывов не делаются вообще.

**LLM.** Сервис работает с любым OpenAI-совместимым шлюзом (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`). Сейчас это AnyModel с моделью `ag/gemini-3-flash`, OpenRouter подключается сменой двух переменных. Ответы резюме и заключений идут через structured output (JSON Schema) и проверяются Pydantic. На битый JSON делается один повтор.

**Похожие игры** считаются без внешних вызовов, детерминированно:
`0.55 · cos(TF-IDF описаний) + 0.30 · Jaccard(жанры) + 0.10 · та же серия + 0.05 · тот же разработчик`.
Индекс строится в памяти и пересобирается, когда меняется набор игр. Под каждой похожей игрой показаны причины: общий жанр, серия, похожее описание.

**Летсплей.**
1. Поиск `"<название> let's play"` через yt-dlp, 15 результатов, без ключа API.
2. Подходят ролики, где в названии есть все значимые слова игры, включая номер части: «Planet Zoo 2» не путается с «Planet Zoo». Ролик длиннее 5 минут, в названии есть признаки летсплея (gameplay, walkthrough, part 1, прохождение и т.п.) или ролик длиннее 20 минут. Трейлеры, обзоры и ролики вида «15 Things You Need To Know» отсекаются. Из подходящих берётся ролик с наибольшим числом просмотров.
3. Речь в текст: первые `LETSPLAY_AUDIO_MINUTES` минут, по умолчанию 8. Способы задаются в `LETSPLAY_STRATEGIES` и пробуются по очереди. `captions`: дорожка автоматического распознавания речи YouTube на языке, на котором говорит блогер. Берётся ровно одна дорожка, потому что запрос всех языков сразу YouTube режет ответом 429. `audio`: вырезка первых минут аудио через yt-dlp и ffmpeg и распознавание в Gemini. `gemini_video`: Gemini получает ссылку на YouTube и Google сам открывает ролик, работает только через OpenRouter. В карточке видно, какой способ сработал.
4. По расшифровке LLM пишет заключение, ключевые впечатления блогера и тональность.

YouTube режет запросы с IP дата-центров по-разному для субтитров, скачивания и поиска, поэтому способов три. Если не сработал ни один, статус игры `blocked` или `failed`, и попытка повторяется при следующих обходах. Если ролик не найден, повтор будет через `LETSPLAY_RETRY_DAYS` дней: новые летсплеи появляются уже после выхода игры.

**Хранилище.** SQLite в режиме WAL на томе Fly. Для одной машины и сотен игр в день этого достаточно, отдельная БД была бы лишней инфраструктурой. Схема создаётся через `create_all`. Если сервис будет расти, следующий шаг: Alembic и PostgreSQL.

**Надёжность запуска.** Одновременно идёт только один запуск: плановый запуск во время ручного пропускается с записью в журнал, а ручной во время планового получает 409 с кодом `RUN_IN_PROGRESS`. Строка запуска закрывается всегда. Запуски, прерванные перезапуском, при старте помечаются как упавшие. Ошибка в одной игре не останавливает запуск. Игры записываются как взятые сразу при выборе, поэтому падение посреди запуска не заставит обход дня пройти их повторно.

## API

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/api/games?q=&platform=&sort=metascore\|userscore\|new\|title&page=` | Список игр |
| GET | `/api/games/{slug}` | Полная карточка с похожими играми |
| GET | `/api/platforms` | Платформы и число игр на каждой |
| GET | `/api/monitor` | Снимок мониторинга |
| GET | `/api/monitor/stream` | Тот же снимок по SSE |
| POST | `/api/runs` | Принудительный запуск: 202, или 409 если обработка уже идёт |
| GET | `/api/runs` | Последние запуски |
| GET | `/api/health` | Проверка здоровья для Fly |

Ошибки приходят в одном формате: `{"success": false, "error_code": "...", "message": "...", "trace_id": "...", "details": {}}`.

## Запуск локально

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
cp .env.example .env          # вписать LLM_API_KEY
.venv/bin/uvicorn app.main:app --port 8000
```

Для летсплеев нужны `ffmpeg` и `deno`: yt-dlp решает через него JS-проверки YouTube. Без ключа LLM сервис всё равно собирает игры, а резюме и летсплеи ждут ключа.

Тесты не ходят в сеть. Парсеры проверяются на фикстурах из реальных ответов Metacritic, пайплайн и API на фейковых клиентах:

```bash
.venv/bin/python -m pytest -q
```

## Как развёрнут

Бесплатные облака, которые держат постоянный процесс, требуют карту (Fly.io) или подписку: Docker-Spaces на Hugging Face доступны только с PRO. С российских серверов не открываются ни metacritic.com, ни YouTube. Поэтому для проверки:

```
браузер → games-digest-lutan.netlify.app ─(прокси Netlify)→ Cloudflare Tunnel ─→ uvicorn на машине автора
```

- Сервис работает на машине автора: `uvicorn app.main:app --port 8800` под `caffeinate`, чтобы машина не засыпала.
- Наружу его открывает `cloudflared tunnel --protocol http2 --url http://127.0.0.1:8800`. QUIC через VPN не проходит, поэтому http2.
- Сайт на Netlify проксирует все запросы на туннель (`/* → https://<tunnel>/:splat 200`). Адрес для проверки остаётся постоянным, даже если туннель перезапустится и сменит адрес.
- Netlify буферизует SSE, поэтому страница мониторинга ждёт событие 5 секунд и переключается на опрос `/api/monitor` раз в 2 секунды. Напрямую через туннель SSE работает как есть.

Для продакшена есть Docker-образ: он проверен сборкой и запуском, `/data` отдаётся пользователю приложения при старте. Есть и `fly.toml`: одна машина в Амстердаме, том под SQLite, health check, без остановки в простое.

```bash
fly volumes create games_data --region ams --size 1
fly secrets set LLM_API_KEY=...
fly deploy
```

## Ограничения

- Пока сервис работает на машине автора, его доступность зависит от этой машины: она должна быть включена и в сети.
- YouTube может блокировать запросы с IP сервера. Тогда в карточке видно найденный ролик и причину, а попытка повторится позже. При переносе в облако понадобится резидентный прокси или YouTube Data API с собственной расшифровкой.
- Распознаётся только начало летсплея, первые 8 минут. Это компромисс между ценой и полнотой: обычно именно там блогер делится первым впечатлением.
- Мониторинг хранит состояние в памяти процесса. На одной машине это работает. При нескольких инстансах понадобится Redis или общая таблица.
